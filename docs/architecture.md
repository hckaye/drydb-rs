# アーキテクチャ

状態: 実装済み。以下の型名・モジュール名・設定名は `crates/drydb` に存在するものを指す。

## 1. 目的と非目的

DryDB 1.4互換の不変ファイルを、必要なページだけ読みながら検索する。書き込みはシード時に完了し、通常のdatabase handleは読み取り専用になる。互換性、安全性、管理メモリ上限を守った上で、読み取りコストを下げる。

全件RAM常駐、全件HashMap化、DB全体のrkyv archive化、全ページの起動時検証は既定動作にしない。SQL、更新API、WAL、MVCC、オンラインのindex追加、汎用トランザクション、DBサーバープロトコルは作らない。

## 2. crate構成

| crate | 責務 |
| --- | --- |
| `crates/drydb` | 形式の復号、page I/O、page directory、cache、B+Tree検索、cursor、副索引、blob、builder、verify |
| `crates/drydb-rkyv` | レコード単位のrkyv codec。coreにrkyv依存を持ち込まない |
| `crates/drydb-msgpack` | MessagePack値のcodecと型付きtable |
| `crates/drydb-async` | tokioのblocking poolを使うasync adapter |
| `crates/drydb-cli` | `drydb` コマンド。inspect / verify / get / range / prefix / count / build |
| `crates/drydb-interop` | C#実装との相互運用テスト。通常のbuildには不要 |

`drydb` の既定featureは空で、依存crateも無い。`mmap` と `zstd` がoptional featureになっている。

## 3. 形式層と検証境界

diskのbyte列を `repr(C)` structへcastしない。長さを検査したslice越しに、`from_le_bytes` 等で明示的に復号する。crate全体が `#![deny(unsafe_code)]` で、例外は `mmap` featureのmapping処理1か所だけになる。

`PageOrdinal`、`FileOffset`、`PageLocalOffset` は別の型にしてある。ファイル側のsigned fieldは負値とsentinelを判定してから内部型へ変換し、加算・乗算・usize変換はchecked演算を通す。

openではheaderとdescriptorだけを読む。descriptor領域は64 KiBから読み始めて、足りなければ `Limits::max_catalog_bytes` まで倍々に広げる。rootとデータページはすべて遅延読み込みになる。

ページをcacheへ入れる時点で、node kind、flags、digest領域、metadata領域、全entryのoffsetとlengthを検査する。未知のflagは受理しない。この検査はbuffer1枚につき1回で、退避されて読み直されればまた走る。検査結果をページ番号やファイルに結び付けて残すことはしないので、「以前このページを検証したから信頼する」という状態にはならない。entryを読む経路は、検査済みかどうかに関わらず、毎回length付きのsliceを通る。

ページの並びも検査する（`OpenOptions::validate_digests`、既定で有効）。形式層はキーのencodingを知らないのでこの検査ができず、木の側で行う。見るのは3点になる。

- 各entryのキーが、encodingから見て形の整ったキーであること。digestが見るのはキーの先頭8 bytesまでなので、後半を失ったキーもdigestは一致してしまう。長さはdigestが代弁できない部分になる。
- 各entryのdigestが、そのentryのキーのdigestと一致すること。
- キーが厳密な昇順であること。これはページ内だけでなく、ページをまたいでも見る。木はページの境界でlayoutが変わりうるので、どちらか片方の規則だけでは境界そのものを見る人がいなくなる。digestから復元したキーは、digestが全単射でないencodingの下では元のキーそのものではないので、どちらかが復元したキーなら同値も許す。digestが同じキーどうしは、各自のdigestが正しいまま順序が入れ替わりうる。検索は二分探索で決めた開始位置から前へ進み、目的のキーより大きいキーで止まるので、順序が崩れていると、ページ上に存在する行を「無い」と答える。

どちらが崩れても、境界を踏み外さないまま結果だけが欠ける。

キーのbyte列を持たないページは、encodingがdigestからキーを復元できる場合にだけ読む。そういうページは比較も復元もdigestだけで行うので、復元できないencodingの下では、digestが一致しただけの別のキーに当たって、そこにある行を返してしまう。復元できるかどうかは `KeyEncoding::max_rebuilt_key_len` で宣言する（既定は `None`）。固定長であることは条件にならない。`uuidv7` と `ulid` のキーは16 bytesで、digestが見るのはその先頭8 bytesなので、digestからキーは決まらない。

キーのbyte列を持たないページでは、キーと突き合わせる相手が無いので、代わりにdigestが昇順であることを見る。digestがキーを一意に決めるencodingでは、同じdigestが2つ並ぶことも拒否する。それは1つのキーに2行あるということで、検索は最初の行で止まり、後ろの行はページにも件数にも現れるのに取り出せない。キーがあるページでdigestの昇順を改めて見ることはしない。digestは順序を保つので、キーが昇順ならdigestも昇順になるし、C#のbuilderが書いた非ユニーク副索引はrecord idまで含めてdigestを計算しており、桁上がりでdigestが減る（互換性仕様のD1）。

検査したかどうかはページのbufferに記録する。同じページは、blobの読み出しにも `verify` にも、同じファイルの別の木からも到達するので、「読み込んだ木が検査する」方式では、先に別の経路がcacheへ入れたページを検査せずに使ってしまう。記録は木ごとに持ち、bufferが退避されれば消える。木が違えばキーのencodingも違うので、別の木の検査結果は流用しない。結果として、1つの木は1枚のページを1回だけ検査する。

Eytzinger配置のページも検査する。digest領域は完全二分木のBFS順なので、その通りの走査でentryと対応付ける。entryを超えた部分は `u64::MaxValue` でなければならない。降下はそこを「どのキーよりも大きい」と見なすので、別の値が入っていると枝の選択が変わる。キーのbyte列を持たないページだけが対象外になる。そこではdigestがキー列そのもので、突き合わせる相手が無い。

葉の兄弟鎖が途中で切れている場合は、走査も件数取得もエラーにする。兄弟が無いというだけでは木の終わりとは言えないので、そのページが木の端のページかどうかを確かめる。確かめないと、切れた先の行が無かったことになり、部分的な答えが全部の答えとして返る。件数も同じ鎖を歩くので、走査と一致してしまい、突き合わせでは気付けない。確認のための降下は走査1回につき1度だけになる。

木の循環と極端な深さは上限で止める。降下は読むページ数で数え、葉も1段に数える。右隣の葉へ進む分は深さに数えない。それは別の走査で、ファイルのページ数という別の上限を持つ。`verify` も同じ数え方をする。数え方が違うと、「検証は通るのに検索できない木」という、どちらの答えより悪い状態ができる。rootからの降下は `Limits::max_tree_depth` 段まで、兄弟鎖の走査はファイルのページ数までに制限してある。全件検証は `Database::verify` として明示的に呼ぶもので、openの中では走らない。`Database::budget` は予算そのものを公開する。rkyv adapterのように呼び出し側のためにメモリを確保する層が、databaseと同じ予算に計上できるようにするため。別々の予算にすると、利用者が設定した値は読み取り全体の費用を表さなくなる。

壊れたファイルを報告するエラーメッセージでも、載せる名前は先頭48 bytesまでにする。名前の長さもファイルが決める値なので、そのまま文字列にすると、破損を報告するまでに予算の外で数百KBを確保することになる。

エラーメッセージに載せるtable名・index名は先頭64文字までにする。名前の長さもファイルが決める値で、しかもこのpassが出すすべてのメッセージの先頭に付く。

エラーメッセージに載せるキーは先頭48 bytesまでにする。キーの長さはファイルが決めるので、2件を丸ごと文字列にすると、それだけで予算の外に数百KBを確保することになる。診断として2つのキーを見分けられれば足りる。

件数の突き合わせも、件数が取れなかった場合は走査側の値で代用しない。代用すると、どちらも走っていないのに一致したことになる。

予算が足りずにpassを続けられなかった場合と、読み取り自体が失敗した場合は、レポートの問題としてではなくエラーとして返す。読めなかったことと、読んだら壊れていたことは別で、前者はファイルではなく呼び出し側の設定や環境の問題になる。一時的なI/O障害を「ページが壊れている」と報告すると、正常なファイルについて誤った答えを返すことになる。

`verify` が返すレポートは、作っている間は予算に計上する。件数の上限（`VerifyOptions::max_problems`）とメッセージ長の上限（512 bytes）を掛けた値は数十KBになり、小さい予算には入らない。1件ごとに、メッセージを作る前に最大額を予約し、入らなければそこで記録をやめて `truncated` を立てる。予約はcacheからの回収を伴う。レポートはこのpassが出す答えそのもので、cacheのページは読み直せるものだから、優先順位はレポートの側にある。長いメッセージは切り詰めるのではなく作り直す。`String::truncate` は容量を保持するので、表示する長さだけが縮んで、確保量は変わらない。passを抜けた後のレポートも計上したままにする。レポートは利用者が持ち続けるメモリなので、予約ごと返し、レポートを捨てたときに予算へ返る。`VerifyReport::is_ok` は `truncated` も見る。途中で止まったpassは「ファイルが健全だと分かった」のではなく「見るのをやめた」のであって、成功として扱えない。CLIの `drydb verify` も同じ判定を使い、1件も記録できずに止まった場合は `incomplete` と表示して終了コード0を返さない。ページ走査と木の走査を両方とも切った呼び出しは `InvalidArgument` で拒否する。何も見ていないpassの空のレポートは、健全だと確かめたファイルと見分けが付かない。

`verify` が使うbuffer（復元したキーと、1つ前のキーの控え）も予算に計上する。検証もキーを復元するので、検索と同じ規則が要る。

`verify` は木を段ごとにたどる。1つの段のページはすべてその段の兄弟鎖の上にあるので、同時に持つページは1枚で済み、検索が偶然降りてこない内部ページも読んで検査できる。子へ降りていく方式だと、段ごとに1枚持つか、木の幅だけのキューが要る。digestとキーの照合は `OpenOptions::validate_digests` の設定に関わらず実行する。この設定を切るのは検索を速くするためで、検証を省くためではない。

rootに兄弟がある場合は報告する。検索はrootから始まり、そこから下と右にしか進めないので、rootの横にページがあるファイルは、木の一部がどのrootの下にも無い状態になる。それ以外の検査は通ってしまう。

digestの昇順は、ページ内だけでなくページ間でも見る。1枚ずつ見ると昇順でも、境界で戻っていることがある。キーを持たないページでは、比較できるのがdigestだけになる。

上の段が並べる子のページ番号と、下の段の兄弟鎖に並ぶページ番号は、同じ並びを2通りに書いたものになる。この2つを1件ずつ突き合わせる。進めるのに必要なのは今見ているページだけなので、追加のメモリが要らない。これで、兄弟鎖が途中で切れている場合、どの親からも指されないページが残っている場合、実在はするが本来と違うページを指している子参照の3つが分かる。子のページ番号がファイルのページ数の範囲にあることも、そのページを読まずに確認する。

各段の子参照については、親が書いた境界キーと、その子の先頭のキー（キーを持たないページではdigest）が一致することも確認する。entryが1件も無いページを親が指している場合も報告する。内部ページが指すのはentryを持つページだけなので、そのページの行がすべての走査から抜け落ちている。ページ番号も兄弟参照も各ページ内の順序も揃っているのに境界キーだけが食い違うと、降下が別の枝へ入り、実在するキーを「無い」と答える。

葉では、値がblob pageにある行について、その参照先がファイル内のblob pageであることも確認する。副索引の各entryが持つPageRefについては、参照先のページにあるレコードの値の範囲と一致し、かつそれが同じtableの主キーの木のレコードであることを確認する。範囲が何かのentryの値と一致するだけでは足りない。副索引自身の値領域を指していても一致してしまい、検索が参照のbyte列をそのまま値として返す。参照先のentryのキーを主キーの木で引き直して、同じページの同じ範囲に行き着くかを見る。値がblob pageにある場合は、そのページがどのtableのものかをページ自身が語らないので、主キーの木をたどるときにそのtableが使っているblob pageをビット列に記録しておき、参照先がその中にあるかを見る。ビット列もファイルのページ数に比例するメモリとして予約する。予約できない場合は、検査を省いて健全と答えるのではなく、passそのものが失敗する。副索引を持たないtableでは、このビット列は確保しない。

レポートが取る予算は、上限の半分までにする。レポートはpassの答えだが、それを作る走査の側にも動く余地が要る。PageRef自体がページに収まらずblob pageへ回っている場合も、そこから読み出して同じ確認をする。読み取り時は、範囲がページに収まることと、ページ先頭のヘッダー領域から始まっていないことだけを見る。どのレコードの値かを突き止めるには参照先のページを走査する必要があり、1行あたりでは割に合わない。葉には参照先のページ番号しか無いので、ページ単位の検査を通り抜けた参照が、blobではないページや存在しないページを指したままになりうる。副索引の木も主キーと同じ手順でたどったうえで、cursorで全件を走査してPageRefの解決も行う。

## 4. I/Oとページディレクトリ

### positional I/Oとbounded cache

検索経路に共有 `Seek` 位置は無い。`PageSource` が位置指定readを抽象化して、短いread、`EINTR`、EOFをそこで扱う。プラットフォームごとの差（`pread` と `seek_read`）はadapter内に閉じている。

`PageDirectory` はordinalから8-byte offsetを取得する。ディレクトリ全体を配列として持たず、既定512 entryのchunk単位で読み、8 chunkまでをLRUで保持する。ページ数に比例する常駐データは既定経路に無い。

ページを読むときは、まず4 bytesだけ読んで格納長を得る。その長さが次のページの先頭を越えていないかも確認する。page directoryの手前で終わっているかだけを見ると、宣言された長さが次のページへ食い込んだファイルで、次のページのbyteがこのページの値として返る。その長さで予算を確保してからbufferを確保し、本体を読む。page filterがある場合は、filterが申告する復号後サイズ（申告が無ければ `Limits::max_decoded_page_bytes`）を確保してから復号し、filterがその範囲を超えて確保していないかを後から検査する。filter自身が復号のために使うメモリも、復号の前後だけ予約する（`PageFilter::working_set_bytes`）。zstdは復号contextをC側のallocatorで確保するので、Rust側からは見えない。同梱のfilterは、その大きさをzstdに問い合わせて申告する（このマシンで95,984 bytes。下限の128 KiBを下回るので、実際に申告するのは128 KiB）。問い合わせにはcontextを1つ作る必要があるので、この測定はプロセスごとに1回だけ行い、結果を持ち回す。測定そのものにもメモリが要るため、filterに問い合わせる前にその分（`PageFilter::probe_bytes`）を予算から予約する。予約できない予算では、filterに何も確保させないまま拒否する。

### mmap

`mmap` featureは別の安全性契約として提供する。ページはmappingからbufferへコピーするので、mapping内部への参照は外に出ない。変わるのはコピーの失敗の仕方で、他のプロセスがファイルを切り詰めるとI/Oエラーではなく `SIGBUS` になりうる。residentなページ量もOSが決めるので、メモリ予算では制御できない。`MmapSource::open` は `unsafe fn` で、ファイルが変更されないことの保証は呼び出し側の責任になる。

## 5. ページ所有権と読み取りAPI

cacheが所有する不変の `PageBuffer` と、利用中の生存を保証する `PagePin` を分ける。`PagePin` は `Arc<PageBuffer>` で、cloneは参照カウントの加算になる。

`ValueGuard` は `PagePin` と検証済みの値範囲を持ち、`as_bytes(&self) -> &[u8]` を返す。借用したsliceはguardより長生きできない。cacheから追い出されてもguardがある間はbufferを再利用も解放もしない。`Database` をdropした後もguardは有効で、`Send` なので別スレッドへ渡せる。

公開APIは次の形になっている。

```text
Database::open(path) -> Result<Database>
OpenOptions::memory_budget(bytes).cache_capacity(bytes).open(path)
Database::table(name) -> Result<Table>
Database::verify(options) -> Result<Charged<VerifyReport>>
Table::get(key) -> Result<Option<ValueGuard>>
Table::get_cached(key) -> Result<CachedLookup>
Table::range(Bound<&[u8]>, Bound<&[u8]>, Order) -> Result<Cursor>
Table::prefix(prefix, Order) -> Result<Cursor>
Table::count_range(Bound<&[u8]>, Bound<&[u8]>) -> Result<u64>
Table::blob_reader(key) -> Result<Option<BlobReader>>
Table::index(name) -> Result<Index>
Cursor::advance(&mut self) -> Result<bool>
Cursor::current(&self) -> Option<EntryRef<'_>>
EntryRef::to_guard(&self) -> Result<ValueGuard>
```

cursorを1つ進める操作は、途中で失敗しても位置を動かさない。副索引のcursorも同じで、内側のcursorを進めてから参照先を読むので、参照先の読み取りが失敗したときは内側の位置も戻す。進めてから読むので、読み取りが失敗したときに位置だけ進んでいると、呼び出し側がメモリを空けてやり直したときに、失敗した行の次の行が返り、その1行が抜ける。失敗する理由として最も多いのは予算不足で、これは呼び出し側が手を打てる種類の失敗になる。

cursorは現在の葉ページ1枚と、値がblob pageにある場合はそのページだけを保持する。結果を `Vec` へ集めることはしない。`EntryRef` はcursorから借用するので、参照を持っている間はcursorを進められない。値を残したいときは `to_guard` でguardにする。キーを格納しないページでは、cursorが持つ小さなbufferへdigestからキーを復元する。

副索引のcursorは行ごとに `PageRef` を解決するので、索引ページと参照先ページの両方を同時に借用しない形にしてある。索引キーはcursorのbufferへコピーし、値は所有権のあるguardとして持つ。

内部ページの降下は、通常はキー以下で最後のseparatorの子を選ぶ。キーのbyte列を持たないページで、かつdigestが全単射でないencodingのときだけ規則を変え、separatorがキーより厳密に小さい最後の子を選ぶ。

この場合、比較はdigestの比較になり、同じ索引キーを持つ行が複数の葉にまたがると、それらのseparatorが同じに見える。さらに、該当する行が葉の途中から始まっていると、比較が等しい最初のseparatorの子に入っても、その手前の子の末尾にある該当行を取りこぼす。右へ進む走査では戻れない。厳密に小さい最後の子から始めれば、最初の該当行と同じかそれより手前に入る。そこから葉の右兄弟をたどって進む。等値検索も、葉の最後のentryがキーより小さい間は同じように右へ進む。この走査はファイルのページ数で上限を置く。

countは値を読まない。葉の中では境界を1回の検索で求め、完全に範囲内の葉はentry countを足す。互換形式に無いsubtree countを追加してO(log N)にすることはしない。

## 6. キャッシュと並行性

cacheはsharded `Mutex<HashMap>` とCLOCK方式の退避で構成する。ページの所有権は `Arc<PageBuffer>` で表す。I/O、復号、値の参照中にcacheのlockは保持しない。

同一ページへの同時missは1回のloadにまとめる。待機側はshardのcondvarで待ち、成功でも失敗でも起こされる。失敗はcacheしない。恒久的に壊れたページでは待機スレッドの数だけ読み直しが起きるが、一時的なI/Oエラーを永続的な失敗として記憶することはない。loadがpanicした場合も、in-flightの印はdrop時に必ず外れるので、待機側が取り残されることはない。

upstreamのGC前提のoptimistic retainはraw pointerに翻訳していない。lock-free化は、reclamationの設計と並行モデルテストを伴う別の作業として残している。

読み取り専用でも、cacheの内部可変性と参照保持の同期は必要になる。「DB全体にRwLockを掛けない」ことと「atomicもlockも不要」は別の話になる。rootページだけは木ごとに保持して、検索のたびのcache参照を1回減らしてある。この保持はページ1枚分を予算へ計上し、予算に余裕が無いときは行わない。保持先は木ではなくpage storeで、木が自分で抱え込むと、後から大きな値を読むときに予算が足りなくなっても取り返せない。storeが持っていれば、cacheと page directory を空にしても足りないときの最後の手段として解放できる。木が破棄されたときも、そのrootの保持は解除する。保持しているrootの表は、entryごとではなく確保済み容量で計上し、entryが減ったら縮める。page storeは、BlobReaderのような利用者が持っている間はdatabaseより長く生きるので、entryごとに計上すると、表の空き枠だけが誰の計上にも入らずに残る。

## 7. メモリ契約

`OpenOptions::memory_budget` が、このcrateが利用者のために確保するbyte数の上限になる。計上する対象は次のとおり。

```text
charged memory = 生存しているpage bufferのcapacity
               + page directory chunk
               + page filterの復号用scratch
               + rkyvのalignment用copy（codecに予算を渡した場合）
```

page directoryが保持するchunkの一覧も同じ扱いで、退避で減ったときに縮める。読み込み中を示す印も、ページが届くまでは他に代わるものが無いので、印を立てる前に予約する。この予約はpage store側で行う。cacheからもpage directoryからも回収する必要があり、その両方を知っているのはpage storeだけになる。予約のための退避も、1回で諦めずに解放が進む間は続ける。clockが最初に選ぶページを木が保持していると、cacheの参照を外してもメモリは減らず、その次のページが本来の解放先になる。同時に読む呼び出しの数だけ印が立つ。

cache自身のentry管理（HashMapとCLOCKのring）は、shardごとに、実際に確保している容量で計上する。ページ1枚あたりの定数では賄えない。shardが1枚しかページを持たなくても表とringは丸ごと1つ分必要で、shardを多く取った構成では、この差が予算を超える分になる。表もringも自動では縮まないので、退避でページが減ったときに、確保済み容量が生存entry数の2倍を超えていれば縮め、縮めた分は予算へ返す。下限は設けない。

表とringは伸びるときに確保するので、entryを入れる前に、入れたことで伸びる分を予約する。伸びるときは新しい領域を確保してから中身を移し、そのあとで古い領域を解放するので、両方が同時に存在する。予約するのは差額ではなく、この同時に存在する分になる。移し終わったら新しい領域の分まで戻す。縮めるときも同じで、小さい表を確保してから大きい表を解放するため、その分を先に予約し、入らなければ縮めずに置く。

cursorは木を生かし続けるので、木はcatalogの予約も持つ。cursorだけが残ってdatabaseが破棄されると、木の分を払った予約だけが返ってしまう。

予約は、対応するbufferを解放したあとで返す。Rustのlocalは宣言と逆順に破棄されるので、bufferより後で宣言した予約は先に返ってしまい、その間、予算は空いていないメモリを空いていると報告する。並行して予約する側はそれを取れるため、合計が上限を超え得る。これはtupleの分解代入と関数の引数にも当てはまる。structのfieldだけは宣言順に破棄されるので、予約はbufferより後ろに置く。

bufferと予約を1つの型にまとめられる場所はまとめる。structなら順序が定義で決まるので、あとから並びを崩しにくい。まとめられない場所（cursorの構築のように、途中で失敗しうる関数へ両方を渡す場合）は、引数の並びで順序を保証し、その理由を書いておく。

表の大きさは、`HashMap::capacity` ではなく、こちらで数えた枠数から計算する。`capacity` は「伸びるまでにあと何件入るか」なので、entryを削ると、領域はそのままなのに値だけが下がる。これを使うと、まだ確保したままのメモリを予算へ返してしまう。逆に、次のentryで作り直しが起きるかどうかは `capacity` でしか分からない。削除で空いた枠は作り直すまで再利用されないので、枠数から見て空きがあっても実際には作り直しになる。大きさは枠数から、作り直すかどうかは `capacity` から決める。

bucket数は件数から計算する。表は全体の8分の1を空けておくので、4件を入れるには8 bucketが要る。件数をそのまま容量として扱うと、縮小先の見積りが1段小さくなる。予約はshardのlockを外した状態で行い、足りなければcacheとpage directoryから回収する。lockを取り直したときに他のthreadが先に伸ばしていた場合、取ってきた予約は古い表に対するものなので、entryを入れる前に今の表と突き合わせ、足りなければ入れずに取り直す。入れてから精算すると、確保したあとで払うことになる。予約できなければ、そのページはcacheに載せずに呼び出し側へ返す。ページ自体は読めているので、載せるかどうかだけの問題になる。

ringへの追加はページを載せる時点で起きるが、そこはshardのlockを持っているので予約できない。そのため、ringに必要な額は、読み込み中のページ数（pending pushes）を数えて決める。載せる時点で予約し直す形にはできない。額は「今の保持数＋これから載せる数」から計算し、その数を収めるためにringが伸びるなら、伸びる先と伸びる前の両方を数える。移している間は両方が同時に存在する。伸びる先は、今の容量を倍にしていって求める。縮めたあとの容量は2のべき乗とも4以上とも限らず、7から伸びる先は8ではなく14、3からは4ではなく6になる。逆に、伸びるときは最低でも4枠は確保されるので、1から伸びる先は2ではなく4になる。

読み込み開始時の容量を基準にしないのは、同時に何本も走っていると、最後の1本が載せる頃にはringが何段も伸びているため。1つの空き枠は1回分にしかならないので、他の読み込みが約束した分も数に入れる。縮めるときも、読み込み中のページの分の枠は残す。残さないと、開始時に空きがあったので予約を省いた読み込みが、載せる段になって枠を失う。

cacheとguardが同じbufferを共有する場合、容量は一度だけ計上する。退避後もguardが保持しているbufferは予算を消費し続ける。ページ数ではなくbyte容量で制御するので、巨大なblob pageも同じ規則に乗る。

範囲の境界キーは、比較する前に検査する。encodingが読めない長さのキーを比較すると、そのbyte列をどう解釈したかがエラーになり、呼び出し側の入力ミスがファイルの破損として返る。

範囲問い合わせの境界キーも予算に計上する。境界は呼び出し側のキーで長さに上限が無く、cursorは自分の複製を持つので、複製する前に予約してcursorが生きている間は計上し続ける。cursorが持つ小さなbuffer（キーを持たないページから復元したキー、副索引cursorが返す索引キー）も同じ扱いになる。復元したキーの分は、復元が書き込む前に予約する。そのために、キーを省略したページを読むencodingは復元後の最大長を宣言する必要がある（`KeyEncoding::max_rebuilt_key_len`、既定は固定長）。宣言が無いencodingは、確保してから超過に気付くことになるので、そのページを読まずにエラーにする。1本あたりはキー1件分だが、cursorは呼び出し側のオブジェクトで、何本でも保持できる。計上するのは中身の長さではなく確保した容量になる。`Vec` に任せて伸ばすと倍々に確保されるので、`reserve_exact` で必要な分だけ確保し、確保後の容量と計上額を突き合わせる。これらの予約もページ読み込みと同じ経路を通るので、足りなければcacheから退避させてから再試行する。予約が退避しないと、同じ問い合わせがcacheの状態次第で成功したり失敗したりする。

cache自身のshard配列も予算に計上する。shard数は呼び出し側が決める値で、配列はdatabase 1つにつき1回確保するので、計上しないと予算の外で増える。配列の分が予算の一定割合に収まるところまでshard数を下げてから確保する。shard数は並行性の設定なので、減らして困るのは競合が増えることだけで、予算が小さいときはページに使うほうがいい。shardごとの表とringは、この配列とは別に、伸びるたびに計上する。

openのときは、headerを26 bytes読んでからdescriptorを読む。descriptorを読むbufferと、そこから作ったtable名やindex descriptorも予算に計上する。計上は解析が終わってからではなく、文字列1本・配列1要素ごとに、確保する直前に行う。あとでまとめて計上する方式だと、「65535個のtableがある」と書いたheaderに対して、予算超過を返すまでにその分を確保してしまう。descriptorが予算に収まらないファイルは、openの時点でエラーになる。

この予約は `Database` ではなく、tableとindexのハンドルを含めた全員で共有する。ハンドルはdescriptorのコピーを持ち、`Database` より長生きできるので、`Database` のdropで解放すると、まだ使われているメモリの分だけ予算が空いたことになる。最後のハンドルがdropされた時点で解放される。

予算が覆わないものは次のとおりで、これはRSSの上限ではない。allocator自身の内部費用、利用者が `to_vec` などでコピーした値、OSのpage cache、`mmap` backendでresidentになったページ。`Database::memory_report` はこの区別を明示して返す。

新規readでは必要な容量を先に予約する。入らなければcacheから退避させて再試行し、それでも入らなければ `BudgetExceeded` を返す。再試行は、何かが解放できている間は続ける。page directoryは1回に1 chunkしか手放さないので、回数を固定すると、まだ回収できるのに失敗を返して、呼び出し側が同じ操作をやり直せば通る状態になる。page bufferとpage directoryのchunkは同じ予算を使うので、どちらの確保も、もう一方から取り戻せる。guardを保持したまま読んだ結果、予算が尽きた場合も同じで、暗黙に待つことはない。エラーには要求量、使用量、上限、そして解放すれば通る見込みがあるかどうかが入る。

メモリ上のimageを開く場合、そのimage自体は予算に計上しない。読む対象そのものであって、ディスク上のファイルと同じ立場になる。数MBのimageを数十KBの予算で開くのは普通の要求で、拒否しない。予算が縛るのは読み取りのほうになる。`open_bytes` に `Arc<[u8]>` 以外（`Vec<u8>`、`Box<[u8]>`、スライス）を渡すと、`Arc<[u8]>` への変換でコピーが起きる。呼び出し側が自分のコピーを持ち続ける場合、大きなimageでは二重に保持することになるので、自分でsourceを組んで `open_source` に渡す選択肢もある。

encodingは、キーの表示（`format_key`）と、その表示を読み戻す処理（`parse_key`）を対で持つ。表示したキーは利用者がそのまま貼り戻すものなので、読み戻せる形で表示する責任は、その表示を決めたencodingにある。CLIの既定（`--key-format auto`）はこの対をそのまま使う。CLI側で「i64なら10進、それ以外は16進」と推測していたときは、`uuidv7` がハイフン付きのUUIDで表示される一方、入力は保存byte列の16進しか受け付けず、一覧からコピーしたキーで検索できなかった。`uuidv7` は表示形式と保存byte列の16進の両方を受け付ける。`ascii` のキーは任意のbyte列なので、表示は印字可能なASCIIだけそのまま出し、それ以外は `\xNN`、バックスラッシュは `\\` にする。`from_utf8_lossy` で表示すると、読めないbyteがすべて同じ文字になり、違うキーが同じに見えて、しかもどちらも貼り戻せない。

openの時点で、木を1段降りるのに必要な最小の予算を検査する。page sizeとdirectory chunkから計算した値を下回る設定は、そこで `InvalidArgument` として拒否する。page filterがあるファイルでは、復号1回分の予約が予算に収まることも同時に検査する。この検査でfilterに必要量を尋ねる前に、尋ねる行為そのものの費用を予約する。

## 8. BLOBと巨大値

overflow格納はupstreamと同じ形で読み書きする。通常の値は葉ページからsliceを返し、blob pageにある値はそのページを保持するguardになる。

`Table::blob_reader` は、ページ全体を常駐させずに値を転送する。転送用のbufferの大きさは呼び出し側が決めるので、確保する前に予約する。読み出す範囲は、ページの長さフィールドだけでなく、そのページがpage directoryの手前で終わることも確認したうえで決める。ファイルから直接chunk単位で読むので、page filterのあるファイルでは使えない（ページ全体を復号しないとbyteの意味が定まらないため）。予算に収まらない大きさのblobでも、この経路なら読み出せる。

rkyvの型付き参照は連続した領域と検証を必要とするので、blobのstreamingと同じ保証はしない。大きすぎるオブジェクトはアプリケーション側で複数レコードに分割する。

## 9. シード・builder

builderとreaderは別の型になっている。`DatabaseBuilder::append` は入力を順不同で受け取り、`sort_buffer` で指定したbyte数までをメモリに溜め、超えたら一時ファイルへ書き出す。build時にそれらをk-way mergeしながら葉を順に生成する。入力全体がメモリに載る必要はない。

`sort_buffer` の値はbuild全体に対する上限で、tableごとの上限ではない。tableを複数宣言しても、副索引を何本つけても、そのときソートに使っているメモリの合計をこの値の内側に保つ。合計が超えたら、いちばん多く抱えているものから一時ファイルへ書き出す。溜める量は、キーと値のbyte数だけでなく、1行あたりの管理情報も数える。キーも値も空の行は管理情報だけなので、byte数だけを見ていると、いくら追加しても書き出しの条件に達しない。

副索引のキーは、その行が載った葉ページを書き出すまで手元に置く。索引に入れる値がページ上の位置なので、ページを書くまで決まらない。待っているキーが割り当て分に達したら、葉ページはその時点の内容で書き出す。ページが満杯でなくてもよい形式なので、少し空きのあるページができる代わりに、待ち行列の大きさが入力に比例しなくなる。

同じ入力からは同じファイルが再現する。副索引のrecord idは、同じ索引キーを持つ行のあいだで主キー順に0から振る。appendした順ではない。C# builderが作るファイルも同じ規則になる。

外部ソートのマージは一度に開くrunの数に上限を置く。これを超える場合は、上限ずつまとめて中間runへ書き出す処理を繰り返してから最終のマージに入る。マージ中に保持するのは、run1件につきキーと値の位置だけで、値そのものはその行を出すときにファイルから読む。sort bufferを小さくしても、マージに必要なメモリが入力全体に比例して増えることはない。書き出したrunの一覧も、溜まった分からその場でまとめ直す。最後にまとめるだけだと、書き出すたびに1件ずつ増える一覧が入力の大きさに比例してしまう。

まとめるのは同じ段のrun同士に限る。runには「何回まとめられたか」を持たせ、同じ段が16本揃ったら1本にまとめて次の段へ上げる。段を見ずにその時点の全runをまとめると、すでにまとめた大きなrunまで毎回読み直すことになり、書き込み量が入力の二乗に比例する。同じ段同士なら、読み書きするのは同じくらいの大きさのものだけで、build全体では段の数だけのpassになる。

一時ファイルを作れなかった場合など、まとめ直しに失敗したときは、取り外した状態を元へ戻してからエラーを返す。戻さないと、次の操作がファイルを探して落ちる。追加した行が書き出しを引き起こし、その書き出しが失敗した場合は、その行を取り消すのではなく、そのspoolを使えない状態にする。書き出しは先に並べ替えるので、行は入れた場所にはもう無く、書き出し終わったあとで失敗することもあるため、取り消せない。以後のappendとbuildはエラーになる。エラーになった追加の行が、あとからファイルに現れてはいけない。

まとめた結果はファイルの末尾へ追記し、読んだ範囲はそのまま残す。残った分が生きている分の2倍を超えたら、生きているrunだけを新しいファイルへ書き直す。ファイルの大きさは入力のおおよそ2倍に収まり、書き直しは前回から倍に増えたときだけ起きる。

副索引のキーは、primary treeを書きながら1行ずつ計算してspoolする。行のPageRefはその行が属する葉を書いた時点で確定するので、両者をそこで組にして書き出す。page directoryのoffsetも追記専用のspoolに溜め、最後にまとめてファイル末尾へ書く。右兄弟ポインタの後方patchは、page directoryを引かずに、同じ段の直前のページのfile offsetを覚えておいて行う。

一意制約、キー長、ページに入らない大きさの入力は、その場で検査してエラーにする。値の長さが `0xFFFF` 以上ならblob pageへ回す。

一時ファイルの名前には、table名などの呼び出し側の文字列を使わない。名前にはパス区切りが入りうるし、ファイル名の長さ制限を超えることもある。受け付けた入力で、並べ替えの途中から失敗するわけにはいかない。出力は一時ファイルへ書き、`sync_all` のあとrenameで公開する。renameの後はUnixで親ディレクトリも `sync` する。クラッシュ後に何が残るかはファイルシステムの性質で、このcrateが保証するものではない。途中で失敗した場合、一時ファイルはdropで削除され、既存のファイルには触れない。

## 10. 測定と最適化

性能の判断は測定に基づく。ベンチマークの構成と、この実装で採用した最適化の前後の数値は[ベンチマーク](benchmarks.md)にある。

現時点で採用しているのは、encoding単位の比較の単純化、木ごとのrootページ保持、副索引cursorのキーコピー削減の3つで、いずれも測定して効果を確認してある。SIMD、lock-free化、dense directory、prefetch、mmapの既定化は採用していない。これらは形式を変えずに試せるが、安全性の証明か測定のどちらかがまだ足りない。

ファイル形式を変える最適化は、1.4互換のwriterには入れない。

## 11. 非同期とエラー

同期版が本体で、`crates/drydb-async` がtokioのblocking poolを使うadapterになる。cacheに無いキーはblocking threadへ渡すために複製するが、キーの長さは呼び出し側が決めるので、複製する前に予算へ予約する（`Database::reserve` / `Table::reserve`）。予約は複製と一緒にblocking側へ移す。futureを捨ててもblocking側は走り続けるので、予約をfuture側に残すと、複製が生きているのに解放されたことになり、開始と取り消しを繰り返すだけで予算をいくらでも超えられる。`Table::get_cached` は、必要なページがすべてcacheにあるときだけ答えを返し、I/Oが必要なら「まだ分からない」を返す。adapterはこれを先に試し、答えが出なければ問い合わせ全体をblocking threadへ移す。futureをdropしてもblocking側は最後まで走るので、page pinも予算予約もsingle-flightの待機者も取り残されない。

エラーの区分は `Io`、`UnsupportedFormat`、`UnknownEncoding`、`UnknownFilter`、`CorruptData`、`BudgetExceeded`、`ValueTooLarge`、`SchemaMismatch`、`ArchiveValidation`、`InvalidArgument`、`Unsupported`。キーが無いことはエラーではなく `Option` で表す。エラーにはページ番号とoffsetが入るが、キーや値のbyte列は入らない。

## 12. 安全性

不正なファイルを入力してもsafe APIからUBに到達しない。`crates/drydb/tests/corrupt.rs` が、有効なファイルの1 byteを書き換えたものと、先頭を切り詰めたものに対して全読み取り経路を実行し、panicも無限ループも起きないことを確認する。

`crates/drydb/tests/miri_smoke.rs` はbuilder、page store、cursor、guardを小さなデータで一周する。Miriの下で動かすことを想定していて、library内のunit testと合わせてMiriで全件通してある。

`drydb-rkyv` のテストは、既定のaliasingモデル（Stacked Borrows）ではMiriが通らない。rkyvの検証コードが使うbytecheckのslice検査が、このモデルでは未定義動作として報告される。新しいモデル（`-Zmiri-tree-borrows`）では20件すべて通る。このcrate自身のコードにunsafeは無く、報告箇所も依存側なので、こちらで直せるものではない。実行するときは Tree Borrows を指定する。

`crates/drydb/tests/concurrency.rs` は、同時missの集約、guardを保持したままの退避、予算の枯渇と回復、guardを持ったままのdatabase dropを扱う。

`crates/drydb/tests/allocations.rs` は、allocatorを差し替えて、cacheに載っている点検索、暖まったscanの1ステップ、暖まったcountが1回もallocateしないことを確認する。cold readはpage bufferを確保するので、この確認の対象外になる。
